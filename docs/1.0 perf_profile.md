# Report: FRNN Benchmark Performance Profile

Profiled on 2026-07-30. The benchmark was rebuilt before measurement so the
binary and report both describe commit `1a12352fe91f`.

## Executive summary

- Warm device latency is **267.829 ms p50** and **270.152 ms p95**, or about
  **3.73 calls/s**, **1.01 million queries/s**, and **34.6 million output
  edges/s** while the result remains device-resident.
- Neighbor search is the bottleneck: its **264.055 ms p50** is **98.59%** of
  warm device latency. Nsight Systems independently attributes **98.5%** of
  aggregate kernel time to `findNeighbors<12, 128, true>`.
- Nsight Compute shows that `findNeighbors` is **latency- and
  divergence-bound**, not DRAM-bandwidth-bound. The kernel reaches 46.39% SM
  throughput and only 9.11% DRAM throughput; schedulers have no eligible warp
  in 55.55% of cycles.
- Long-scoreboard stalls consume about **8.3 of 15.7 cycles between issued
  instructions (52.7%)**. Despite 85.75% achieved occupancy, only 0.83 of
  6.97 active warps per scheduler is eligible to issue on an average cycle.
- Control-flow efficiency is also low: only **17.07 of 32 threads per warp**
  are active on average. This agrees with the per-query variation in visited
  grid cells, distance early exits, accepted candidates, heap operations, and
  final heap sorting.
- Grid construction, point reorder, edge count/scan/write, and count copy
  together are only about **1.47%** of p50 device time. Optimizing or fusing
  those stages cannot materially improve this workload.

## Bottleneck analysis

The hot kernel assigns one query to one CUDA thread. That thread walks a
query-dependent four-dimensional cell range, rejects corner cells, iterates
each surviving cell's candidates, performs a reordered 12-dimensional
distance screen with early exits, and serially maintains and sorts a K=1000
neighbor heap. Neighbor rows also live in a large global-memory workspace.

This structure explains the profiler evidence:

1. Candidate and heap accesses form dependent load/use chains, producing
   long-scoreboard stalls even though the caches have high hit rates and DRAM
   bandwidth is lightly used.
2. Neighbor density and cell occupancy differ by query. Threads in the same
   warp therefore visit different cell/candidate counts and take different
   distance-screen, acceptance, and heap paths, leaving about half the warp
   inactive on an average cycle.
3. One thread performs all top-K maintenance for its query. High occupancy
   cannot hide enough of these serialized dependencies because most resident
   warps are stalled at the same time.

## Memory profile

The benchmark's reusable workspace reserves about **2.059 GiB before CUB scan
scratch**, dominated by the 2,173,304,000-byte distance/index neighbor arrays.
Its device fixture also reserves conservative `N × K` edge capacity, making
the fixture about **4.060 GiB** including its input. The steady benchmark
therefore holds at least **6.119 GiB** before scan scratch and CUDA runtime
overhead.

Only 9,279,672 edges are produced (141.6 MiB), so the fixture's 4.05 GiB edge
buffer is deliberately conservative. This is a benchmark/device-API capacity
choice, not the synchronous host API behavior: the latter uses count-first
allocation for exact output size. Memory capacity is not the measured runtime
bottleneck, but the conservative fixture limits how much concurrency can fit
on this 8 GiB GPU.

## Optimization priorities

1. **Parallelize or restructure per-query candidate selection.** A
   warp-/group-cooperative exact top-K design is the only change with a
   plausible large end-to-end payoff because it can attack both serialized
   dependencies and inactive lanes. It must preserve canonical float32
   distance order and `(distance, index)` tie-breaking.
2. **Reduce or better balance candidate work.** Measure candidate counts per
   query, then evaluate better high-dimensional grid-axis selection or a work
   queue for heavy queries. The current grid indexes only four of twelve
   coordinates; improvement is plausible but should be validated against the
   existing exactness and broad-distribution tests.
3. **Do not prioritize setup fusion, scan replacement, CUDA Graph capture, or
   edge-write tuning for this workload.** Even eliminating every non-search
   stage would improve p50 by only about 1.4%.
4. **Keep workspace reuse.** Recreating it costs about 45 ms p50. Applications
   needing repeated low latency should continue to reserve once and use the
   asynchronous device API.

Any search redesign should be evaluated first against the exact real edge set,
then with this same 30-iteration command. The profiler indicates where time is
lost; only the native CUDA-event distribution should be used to claim an
end-to-end speedup.
