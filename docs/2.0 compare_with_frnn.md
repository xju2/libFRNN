## Comparison

Run the reproducible comparison with:

```bash
.venv/bin/python tests/compare_frnn_packages.py
```

The previous measurements on an RTX 2070 SUPER use seeded uniform 3D points,
radius chosen for eight expected neighbors, `max_neighbors=32`, five timed
iterations, and the median latency:

| Points | Directed edges | Edge agreement | `frnn_cuda` host ms | `frnn` GPU ms | `frnn` host ms |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 74,764 | 100% | 1.200 | 1.071 | 1.406 |
| 100,000 | 774,610 | checked at 10k | 14.289 | 1.849 | 4.368 |

`frnn_cuda` host timing is its public synchronous NumPy API, including input
and compact edge-output transfers. `frnn` GPU timing keeps the input and padded
neighbor indices on the GPU. Its host timing additionally copies NumPy input
to CUDA and padded indices back to the CPU. The output representations differ,
so the GPU column is an intentional best-case PyTorch comparison rather than
an identical boundary-cost comparison.

At 10k points, the edge sets match exactly and `frnn_cuda` is slightly faster
than the original host round trip. At 100k points, the original is about 3.3x
faster including its host round trip and 7.7x faster with tensors kept on the
GPU. The current `frnn_cuda` Python binding is therefore attractive when a
small NumPy-only dependency surface and compact edges matter; original FRNN is
better for large PyTorch-resident workloads.

### NERSC A100 rerun (2026-08-05)

The comparison was repeated in interactive allocation `56390488` on NERSC
Perlmutter node `nid001096`, using one NVIDIA A100-SXM4-40GB GPU. The software
environment was Python 3.12.11, NumPy 2.5.1, PyTorch 2.8.0+cu129, CUDA 12.9,
and NVIDIA driver 580.159.04. All CUDA extensions were compiled specifically
for SM80 in the same `uv` virtual environment. Source revisions were
`ea17cadee159` (`libFRNN`), `050dd0d9cc26` (original FRNN), and
`008f3239e3f3` (`prefix_sum`).

The environment was created and populated on the interactive GPU node with:

```bash
module load pytorch/2.8.0
export UV_CACHE_DIR=/tmp/frnn-uv-cache
uv venv --python "$(which python)" --system-site-packages .venv
uv pip install --python .venv/bin/python \
  'scikit-build-core>=0.10' 'pybind11>=2.11' setuptools wheel

export CUDA_HOME=/opt/nvidia/hpc_sdk/Linux_x86_64/25.5/cuda/12.9
export CUDACXX="$CUDA_HOME/bin/nvcc"
export CC=/opt/cray/pe/gcc-native/13/bin/gcc
export CXX=/opt/cray/pe/gcc-native/13/bin/g++
export CMAKE_ARGS='-DCMAKE_CUDA_ARCHITECTURES=80'
export TORCH_CUDA_ARCH_LIST=8.0
export NVCC_FLAGS='--std=c++17'

uv pip install --python .venv/bin/python --no-build-isolation -e .
uv pip install --python .venv/bin/python --no-build-isolation \
  ./third_party/prefix_sum
uv pip install --python .venv/bin/python --no-build-isolation \
  ./third_party/FRNN
```

The prefix-sum CUDA smoke test again produced `[0, 1, 3]`, and all 12
`frnn_cuda` Python tests passed. After one process-level warm-up run, two full
comparison runs closely agreed. The final run was:

| Points | Directed edges | Edge agreement | `frnn_cuda` host ms | `frnn` GPU ms | `frnn` host ms |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 74,764 | 100% | 1.326 | 1.280 | 1.566 |
| 100,000 | 774,610 | checked at 10k | 6.611 | 1.439 | 3.624 |

The preceding confirmation run measured 1.328/1.296/1.593 ms at 10k and
6.615/1.466/3.664 ms at 100k for `frnn_cuda` host / `frnn` GPU / `frnn` host,
respectively. On the A100, `frnn_cuda` is 1.18x faster than the original host
round trip at 10k. At 100k, original FRNN is 1.82x faster including its host
round trip and 4.59x faster with tensors kept on the GPU.

### NERSC A100 real-data rerun (2026-08-06)

The supplied `data/embedding_data.csv` workload was run in interactive
allocation `56404233` on Perlmutter node `nid001101`, again using one
NVIDIA A100-SXM4-40GB GPU and the same `uv` environment. The input contains
271,663 points with 12 dimensions. Both implementations used radius 0.12 and
1,000 non-self neighbors and matched all 9,279,672 directed edges in
`data/edge_list.csv` exactly.

The real-data comparison is reproducible with:

```bash
.venv/bin/python tests/compare_frnn_packages_real.py
```

Each timing is the median of five iterations after a warm-up call. The final
run was:

| Points | Dimensions | Directed edges | Edge agreement | `frnn_cuda` host ms | `frnn` GPU ms | `frnn` host ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 271,663 | 12 | 9,279,672 | 100% | 192.966 | 243.913 | 553.933 |

The preceding confirmation run measured 203.461/243.971/544.966 ms for
`frnn_cuda` host / `frnn` GPU / `frnn` host. In the final run, the original
GPU-resident path took 1.26x as long as `frnn_cuda`, while its host round trip
took 2.87x as long.

As in the synthetic comparison, the output representations differ. The
`frnn_cuda` host result is a compact `2 x 9,279,672` edge array (about 148 MB).
Original FRNN returns a padded `271,663 x 1,001` index tensor; its host timing
copies about 2.18 GB of indices back to the CPU. The GPU timing avoids that
copy and is the more favorable original-FRNN measurement.

| Capability | `frnn_cuda` | Original `frnn` |
| --- | --- | --- |
| Python dependency | NumPy | PyTorch and `prefix_sum` |
| Python input/output | NumPy points / compact edge list | Batched CUDA tensors / padded distances and indices |
| Autograd | No | Distance gradients |
| Native use | C++/CUDA host, device, and async APIs | PyTorch CUDA extension |
| Same-set output | Directed or unique undirected, optional self exclusion | Directed per-query neighbors, including self unless filtered |
